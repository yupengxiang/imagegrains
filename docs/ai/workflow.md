# 多 Agent 工作流

本文档定义 planner、executor、reviewer 角色如何通过 `docs/ai/` 协作。

## 共享规则

- 以仓库事实为起点：做假设前先检查相关文件（`docs/ai/`、`docs/data-flow.md`、`docs/architecture.md`、`docs/task.md`）。
- 保留工作树中与任务无关的脏改动。
- 改动保持外科手术式的最小范围，严格对应当前任务。
- 验证遵循 `docs/ai/testing.md`。
- 不改变公开接口、CLI 选项、输出格式（CSV 列名/文件命名约定）或引入重型依赖，除非有明确的兼容性讨论。

## 开始新任务

1. 读 `docs/ai/project-overview.md` 了解项目背景。
2. 若任务涉及架构、数据格式、输出契约或公开接口，读 `docs/ai/DECISIONS.md`。
3. 若任务影响竞赛行为，读 `docs/task.md`。
4. 检查 `git status --short`。
5. 检查最小的相关代码/配置路径。
6. 非平凡任务先说明假设与范围再动手。

## 继续已有工作

1. 读 `docs/ai/HANDOFF.md`。
2. 读 `docs/ai/PLAN.md`。
3. 检查 `git status --short` 和相关 diff。
4. 从文档化状态继续，不要重启任务。
5. 若 `PLAN.md` 与实际代码冲突，先停下来报告不一致，再编辑。

## Planner 角色

Planner agent 应该：

- 澄清目标、成功标准、约束以及范围内/范围外的边界。
- 在提问前先检查仓库内能回答的事实。
- 为实质性工作产出决策完备的计划。
- 识别兼容性风险与验证命令。
- 规划阶段不做实现编辑。

好的 planner 输出包括：

- 要改动的具体文件或子系统；
- 预期的行为变化；
- 来自 `docs/ai/testing.md` 的验证命令；
- 假设与风险；
- 明确的非目标。

## Executor 角色

Executor agent 应该：

- 编辑前阅读当前计划、编码风格与测试指南。
- 只实现当前计划范围内的内容。
- 优先复用现有模式（`src/imagegrains/` 现有函数），不发明新抽象。
- 行为变化时新增或更新测试。
- 运行最小的相关验证。
- 任务实质、未完成或要交接时更新 `docs/ai/HANDOFF.md`。

若执行中发现计划错误，停下来更新用户或交接记录，而不是硬推计划。

## Reviewer 角色

Reviewer agent 应关注：

- 正确性 bug；
- 回归；
- 接口/数据格式/CLI 兼容性风险（尤其是 CSV 列名、mask/grains/gsd 文件命名约定）；
- 缺失或不足的验证；
- 意外的广泛改动；
- 与脏工作树状态的交互。

评审意见应具体，尽量带文件与行号引用。

## 交接协议

切换 agent、结束实质性工作或留下未完成工作前，更新 `docs/ai/HANDOFF.md`，包含：

- 任务目标；
- 已完成步骤；
- 改动文件；
- 重要决策；
- 已运行的验证命令；
- 已知问题；
- 下一步建议。

保持 `docs/ai/PLAN.md` 与实际状态一致。工作完成后，`PLAN.md` 可以指向下一个文档或实现优先级，而不是过时的已完成步骤。

## TODO 协议

- `docs/ai/TODO.md` 记录跟进想法与已知问题。
- TODO 项不是自动的实施许可。
- 实施 TODO 前，必须由用户或当前任务显式选择。
- TODO 完成时移除或标记为完成，必要时更新交接记录。
